# 设计说明

## 问题

订单域与结算域由不同系统独立维护，侧写（order_id）只有业务批次是两边共同的、已确认的关联键。
没有共享事务，也没有全局时钟。需要一个报告查询端同时读取两边，并回答三个问题：

1. 这次报告到底选了哪两个版本，依据是什么？
2. 无法对齐时，是等、退、还是给不完整结果？
3. 正在读的快照会不会被修订或 GC 掉？

## 不变量

- **同批不变量**：跨域记录只来自 `batch_id` 相同、`confirmed=true`、且通过 checksum 校验的两个快照。
- **可追溯**：每份报告携带 `selection`（批次、版本、checksum、是否该域最新、滞后批次数）、
  `domains`（可达性、最新批次）、`leases` / `lease_release`、`uncovered`。
- **不伪造**：部分结果模式下 `records` 为空，只有元数据与未覆盖范围，不产生单域合计。
- **租约不被旧任务破坏**：释放必须匹配 `lease_token`；GC 跳过所有活跃租约快照。

## 一致性模型

这是**已确认批次的快照隔离**，不是线性一致或可串行化：

- 每个域独立发布不可变快照；`confirmed` 表示该批在本域已完成写入。批次可以先以
  `confirmed=false` 发布，再由 `POST /admin/confirm/{batch}` 转为已确认；未确认快照不参与选版。
- 协调器在两边已确认集合的交集中选最大 `batch_id`，因此两侧永远同一业务批次。
- 如果两域最新批次不同，说明有一边在线推进；协调器在 `max_wait_ms` 内轮询等待落后一方追平，
  超时后按策略退回共同旧版（默认）或 503（strict）。
- 任一域不可达时不再轮询：重试一个已停机的服务只会空耗截止时间，立即返回 `partial`。

实现上，「等待多久」与「等不到怎么办」是两件事：轮询只在两域都可达、且存在共同已确认批次
（即理论上有机会对齐）时进行；对齐或到达上限后，选版规则只做一次决定。

### 为什么不是各自最新

各自最新版本可能属于不同业务日期、不同批次的修订周期。拼接会：
- 让结算金额与订单金额来自不同日切；
- 让同一 `order_id` 在两侧金额口径不一致；
- 在审计上无法解释某个数字来自哪个批次。

退回共同旧版是有代价的（数据较旧），但代价是**可度量**的：`freshness.lag_batches` 与
`uncovered.batch_gap` 明确告诉你落后多少、漏了哪些批次。

## 租约协议

```
coordinator                       orders / settlement
    │  GET /batches                  │
    │───────────────────────────────>│
    │  POST /pins {snapshot_id,      │
    │    owner, lease_token, ttl}    │
    │───────────────────────────────>│  插入 pins 行
    │  GET /snapshots/{b}/{v}        │
    │───────────────────────────────>│
    │  POST /pins/{pin_id}/release   │
    │    {lease_token}               │  校验 token 后标记 released_at
    │───────────────────────────────>│
```

- `lease_token` 每次运行随机生成，域服务只接受完全匹配的 token。
- 过期 token（例如上一个协调任务持有的 token）释放时返回 409，租约保持活跃。
- TTL 到期后域服务在下一次访问时惰性清扫，不依赖协调器存活。
- GC 只处理 `version < max(version) for batch` 的旧版本，并在同一写锁内读取活跃租约集合。

## 故障场景

| 场景 | 行为 |
|---|---|
| 结算域停机 | 报告 `partial`；订单域仍可推进、仍可查询健康；协调器不尝试等它恢复 |
| 恢复后两域批次不同 | `degraded_stale`，退回最后共同已确认批次 |
| 两域已发布同一批次但未确认 | 该批次不参与关联；等待窗口内确认完成后自动对齐（`attempts` 记录轮询次数） |
| 恢复后两域批次相同 | `aligned` |
| 协调器停机 | 网关返回 503 且不直接读域数据，避免绕过一致性规则 |
| 修订正在读的批次 | 已加租约的旧版本不被 GC；新查询看到新版本 |
| 旧任务用旧 token 释放 | 409，租约仍保护快照 |
| strict 模式不对齐 | 503 `strict_failed`，响应含 `chosen_batch` 与 `lag_batches` |

## 可扩展点

- 生产环境可把域服务换成真实数据库的 snapshot 导出，保留 `batch_id + version + checksum` 契约。
- 协调器的批次读取可改为事件驱动（两域发布事件，协调器维护共同已确认水位），
  当前轮询实现把等待上限和降级规则留在了同一处。
- 长任务租约应加自动续租线程；当前演示由调用方在 TTL 内显式释放。
